# Windows / macOS 跨端交接

用于 Windows 与 macOS 之间的项目核对、远程接续或工作副本迁移。遵循[生命周期与协作流程](lifecycle-and-collaboration.md)的版本与归属规则。按项目已有配置选择 UU 端口映射下的 SSH／PowerShell／文件传输或 GitHub；两条路线可以组合，但每次明确哪些内容通过哪条路线交付。

## 先确认交接的是哪一份工作

先辨明执行位置：Mac 上的 Agent 通过 SSH 继续操作 Windows 原目录时，项目仍在 Windows；只有把工作副本迁到 Mac，才需要建立 Mac 目录映射与运行环境。聊天所在机器、命令执行机器和项目文件所在机器分别记录，不能混为一谈。

最小交接记录包含：

| 字段 | 记录内容 |
| --- | --- |
| 项目与机器 | 已确认的项目标识；源／目标机器别名与系统，不能仅凭项目同名匹配 |
| 文件位置 | 两端实际项目根目录，当前权威工作副本及负责人；迁移前未建目标目录时注明待核对 |
| 路线与连接 | UU 或 GitHub，远程原地接续或迁移；使用已配置的连接别名，不写密码、令牌或私钥 |
| 基准 | 状态修订、相关决定、提交或关键文件哈希，以及快照对应时间和时区 |
| 文件缺口 | 未提交、未跟踪、忽略文件和仓库外资产中影响接续的内容；实际存放位置与传递方式 |
| 环境与运行 | 必要工具／依赖、配置来源、实际运行的后台任务及其机器、可查询编号和日志位置 |
| 交接状态 | 待核验、待转移或已接手；目标核验结果、范围和所有权转移点 |

连接信息通过现有受控配置使用；需要敏感配置的项目只记录配置来源与可用性，不复制秘密。状态文件若未纳入仓库或传输材料，必须另行明确如何交给目标端。

## 路线 A：UU 端口映射与 SSH / PowerShell / 文件传输

UU 提供网络可达性，SSH 负责登录和命令执行，文件传输负责复制材料。三者的成功分别核对，不能由“端口通了”推断“已登录”或“文件已一致”。

1. 使用项目已确认的连接别名和映射，核对实际登录机器、系统、目标路径和当前负责人。映射失效时核对现有配置，不猜端口或连接其他机器。当前用户未授权远程操作时，仅整理交接材料。
2. 远程原地接续：在原机器核对权威目录、状态修订、实际文件和后台任务；无需把项目复制到聊天所在机器。交接负责人变化仍需遵循先停止旧写入、再开始新写入的规则。
3. 跨机迁移：先收拢源端对本次范围的写入，形成稳定文件版本，列出需要传递的状态文件、源码、文档、必要资产与版本依据。仅传任务所需材料；本机环境与敏感配置按目标端已有方式重建。
4. 使用已支持的传输工具复制到目标端隔离目录或确认安全的目标位置；先核对目标现有改动，不直接覆盖。按重要性核对文件清单、大小及内容哈希；版本变化或传输中断时不得把部分文件标成完整迁移。
5. 在目标系统使用相符的路径和命令语法：Windows 端按实际 PowerShell 版本运行，Mac 端按实际 shell 运行；路径参数正确引用。按任务检查大小写、换行、执行权限、符号链接或 Windows 文件名限制等实际差异，不把源端虚拟环境、进程或机器路径当作可直接搬运的运行状态。

后台任务继续运行在原机器时，单独记录谁负责观察、产物在哪及如何取得；复制项目文件不等于迁移进程。断线时任务可能仍运行，先查询再决定重试，避免重复启动同一任务。

## 路线 B：GitHub 提交同步

1. 核对仓库、分支、源端当前提交及远端实际提交。检查任务范围内的未提交、未跟踪与忽略文件；逐项区分需要带走、目标端重建和留在源端。不要为得到干净目录而丢弃改动。
2. 在已有提交／推送授权内，把本次需要同步的文件形成可追溯提交并推送；没有同步授权时保留材料并明确缺口。记录实际远端提交 SHA，不能把本地提交成功当作推送成功。技能默认保存行为本身不授权上传项目。
3. 目标端已有工作副本时，先核对其未提交改动与分支差异，再更新；需要新副本时使用已确认仓库。将接续基准固定到已核对提交，不能仅写“拉取最新”。不以强制推送、硬重置或清理目录解决交接差异。
4. 按项目需要核对子模块、Git LFS 对象和构建所需资产是否实际取得；GitHub 未包含的大文件、数据、配置和状态文件按已授权方式补齐。GitHub 成功只证明对应提交可取得，不能证明项目完整可运行。

## 目标核验与归属转移

目标端先只读核对项目身份、路径映射、基准提交或哈希、状态修订、相关决定及必要文件。随后在隔离位置或确认的目标工作范围做适当的依赖检查、构建、测试或文档打开验证，记录实际结果与未执行项。若核验会改写双方共享的业务目录，先与当前负责人划定核验范围。

源端冻结后若又有更新，原快照不再代表当前交接状态；重新核对增量并记录基准，不能保留旧回执声称已全部接手。目标具备执行条件且源端已停止同一范围写入后，记录所有权转移点，再允许目标继续修改。原地远程接续可保持同一权威目录；迁移完成后明确新权威副本与仍留在源端的依赖。不能让两端在不知情的情况下各自推进同一范围。

核验失败时保留原权威副本与负责人，标明缺项；转移结果未知时先查两端运行与文件状态。无法确认旧写入已停止时冻结重叠范围，不能因超时就启用另一端写入。

UU 不可用时可以在已有授权内评估 GitHub 路线，但仅当所需内容确已同步并能在目标端取得时才可切换；GitHub 缺少资产时可用已配置的 UU 文件传输补齐。路线切换不改变项目身份、授权范围、验证标准或归属规则。

## 跨端走查

- Mac 连接 Windows 原目录继续工作，权威文件位置仍是 Windows。
- GitHub 已同步但状态文件、未提交改动或仓库外数据未到目标端。
- UU 传输中断或 SSH 断线，但原机器任务仍运行。
- 目标已有独立改动、基准不一致，或两端路径与运行环境不同。
- 目标核验后源端又写入新内容；旧回执不能支持转移。
