# 生命周期与多 Agent 协作

在已有多人、多 Agent 或跨聊天交接任务时读取。本文约定交付与汇总方式，不提供调度器、锁或事务，也不自行授权创建 Agent、聊天或发送消息。普通单人保存无需创建协作表和交付目录。

## 决定与任务分别演变

决定记录当前约束及其来源，任务记录执行进度；两者不能互相代替。

- 决定：待确认 → 有效 → 已取代或已撤销。采用自行假设时保留其来源类别；已核验的实现不会自动把假设变成用户确认。
- 新方案仅为候选时，原有效决定继续成立；用户已明确撤销时旧决定立即失效，即使尚无替代方案。失效决定若重新采用，创建新编号并引用历史，不覆盖原记录。
- 取代关系指向真实存在的决定，连续替代可沿编号追溯，不允许自指或循环。决定和任务编号由指定写入者分配，已有项目编号继续沿用。
- 任务：未开始 → 已派发 → 执行中 → 已交付 → 已核验。阶段须有实际证据；只有发出任务时记录已派发，只有实际工作证据才记录执行中。交付被退回时可回到执行中，保留退回原因和旧交付引用。
- 受阻、失败或取消记录原因、最后可核对阶段与影响；工具无法查询时标未知。取消任务不等于停止运行，取消决定也不等于撤销已经产生的外部结果；实际运行与结果分别核对。

## 分工与指定写入者

优先沿用项目已有的负责人和记录方式。协作开始前明确谁维护总状态、各任务可修改哪些文件或范围、依赖哪些决定、预期交付和验收条件。存在重叠写入时先划分范围，不能仅靠“各自注意”避免覆盖。

各执行者可在划定的独立范围工作，交付证据和总状态修改建议；总状态只由指定写入者汇总。没有共享存储时可使用宿主允许的交付消息或可访问材料，不能声称已写入另一个工作区。不为此改变现有通信权限。

Markdown 文件本身不提供并发协调。无法确定唯一写入者时，先收拢为顺序更新，暂不并行修改总状态。写前重读和临时文件替换均不能阻止另一写入者用旧版本覆盖。确需多写入者时，必须由实际后端提供并验证版本比较、锁或事务；没有该能力就明确保留单写入者限制。

## 基准版本与交付

协作项目在总状态记录修订号与指定写入者，例如 R7；每次有效汇总后递增。它是本地维护的版本标签，不是锁或可信身份凭据；来源版本还应按需附提交、文件哈希或实际产物版本。

派发任务时记录：

- 稳定任务编号（如 T1）、负责人和宿主返回的真实查询编号；两种编号分别标注，不能编造查询能力。
- 可修改范围、依赖与完成标准。
- 当时的总状态修订、相关决定编号及所需成果版本。

交付采用现有项目格式；缺少格式时包含以下最小信息即可：

| 字段 | 内容 |
| --- | --- |
| 任务与交付版本 | 如 T1 / v1；更正内容使用 v2，不覆盖已发布 v1 |
| 基准 | 开始时的总状态修订、相关决定编号及关键文件版本 |
| 产物 | 文件或提交、实际版本和修改范围；未提交改动明确标注 |
| 验证 | 实际执行的检查、结果、未做的检查与证据位置 |
| 缺口 | 未决问题、冲突、阻塞与剩余风险 |
| 汇总建议 | 建议更新哪些事实或决定；建议不自动生效 |

旧交付需要可追溯。使用会变化的文件路径时同时记录版本，必要时保留交付快照；不保存凭据或完整聊天。交付缺项影响核验时标已交付但尚未核验，不把执行者自报成功当作核验结论。

## 汇总、过期与重复交付

指定写入者按以下顺序处理每份交付：

1. 重读最新总状态，核对任务、负责人、修改范围与成果可达性。核对交付基准及依赖决定是否变化，不仅比较修订号大小。
2. 修订变化但与交付无关时，可在说明核对结果后合入；相关决定、文件或依赖已变化时，先检查受影响部分，必要时要求重做。保留原始基准，不把旧交付改写成基于新版本产生。
3. 依据交付内容做适当验证。实现与用户决定不一致时，记录实现偏差，不能反过来宣布用户决定失效。证据冲突时保留各方来源，只暂停依赖冲突的动作；明确规则内可解决的直接处理，需要用户裁定的具体问题再询问。
4. 在同次保存中更新已接受的成果、任务阶段和决定变更，标记已处理的任务／交付版本、处理结果及新修订号。新旧决定的变更一并写入，并回读核对。处理过的同一交付版本不再次应用；同一版本却内容不同视为冲突，要求发布更正版。

写入结果不明时先回读，确认交付处理标记与修订是否已生效再重试；没有共享可读状态时明确结果未知，不重复触发外部动作。此处约定的是文件记录的一致维护，外部发布或不可逆操作仍以实际接口、当前授权和回执为准。

## 负责人移交与失败恢复

移交记录源／目标负责人、范围、当前修订、已派发但未合入的交付和实际运行任务。移交等待中由源负责人维持归属；接手方先只读核验，不立即修改业务文件。

接手方确认准备就绪后，源负责人收拢在途写入，记录交接边界，并在接手方开始写入前停止修改同一范围。总状态写入权也移交时，停止旧写入者后再启用新写入者；用双方可访问记录或工具回执核对转移点。没有可查询回执时标待接手或未知，不报告已经接手。

接手失败、失联或结果未知时，先查询实际运行和文件变动。只有确认接手方已停止或能够可靠隔离其写入后，才把范围交回源负责人或另派；暂时无法确定时冻结重叠范围，继续不依赖它的工作。不能单凭超时推断对方停止。

## 演练关注点

变更本流程时，以隔离材料走查以下场景；静态检查不等于真实并发或权限验证：

- 用户撤销旧决定但没有替代；候选方案未确认；连续替代后恢复。
- 两个任务基于同一修订，先后交付；一个交付的相关决定已被取代，另一个仅遇到无关修订。
- 同一交付重复到达、同一版本内容不一致、汇总写入后回执丢失。
- 执行者称已完成但证据不足；用户验收尚未发生。
- 接手失败且旧任务仍运行；指定写入者切换期间存在在途写入。
- 已完成任务归档后，其有效约束和成果仍能在活跃区找到。
